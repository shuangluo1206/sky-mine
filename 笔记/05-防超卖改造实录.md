# 05 - 防超卖改造实录（复现 → 修复 → 数据对比）

> 时间：2026-10-02
> 位置：外卖项目阶段二改造 item 3 第一枪
> 结论：库存 5 / 并发 20 → 修复前卖出 11 单（库存 -6），修复后恰好 5 单（库存 0），**零超卖**

---

## 〇、总览

课程代码没有库存概念（dish 表无 stock 字段，下单不校验数量），本次改造三步走：

```
① 建库存：dish 加 stock 字段 + 下单先查后扣（朴素实现，故意留并发窗口）
② 复现超卖：20 个测试用户并发下单，库存 5 → 成交 11 单、库存 -6（截图实证）
③ 修复：Redis 分布式锁包住整个事务，同场景复压 → 成交 5 单、库存 0
```

**一句话简历**：为下单接口设计 Redis 分布式锁防超卖方案，先以并发压测复现超卖
（库存 5 被打出 11 单成交、库存 -6），修复后同场景零超卖；锁粒度、自旋重试、
事务提交边界（锁必须包住 @Transactional 的提交）均经过实测验证。

## 一、超卖是什么：check-then-act 竞态

```
青椒肉丝 库存 = 1

0.1s  请求A 读到库存=1 → 判"够" → 下单 → 扣减
0.1s  请求B 同时读到库存=1 → 判"够" → 下单 → 扣减
（两人基于同一份旧值做判断，都成功）

结果：卖出 2 份，库存 0，但只有 1 份的货
```

根源：「查库存」和「扣库存」是两步，中间没有互斥。黑马点评优惠券秒杀同款问题。

## 二、① 建库存（+42 行 / 5 文件）

| 文件 | 改动 |
|---|---|
| `dish` 表 | 加 `stock INT NOT NULL DEFAULT 0`，存量 24 菜初始化 100 |
| `Dish` 实体 | 加 `stock` 字段 |
| `MessageConstant` | 加 `DISH_STOCK_NOT_ENOUGH = "菜品库存不足，无法完成下单"` |

- **套餐（setmeal）不做库存**——本轮范围只做 dish，注释写明
- **判断和扣减故意分两步、SQL 故意不加 `stock >= #{num}` 条件**——留给②压测打穿用

## 三、② 压测复现（20 并发，一炮命中）

压测构造：20 个测试用户（SQL 直插 user/address_book/shopping_cart），
每人购物车 1 份「老坛酸菜鱼」，库存设 5，python 生成 20 个 JWT 后 curl 同时发。

### 结果

| 指标 | 数值 |
|---|---|
| 初始库存 | 5 |
| 并发请求 | 20 |
| **实际成交** | **11 单**（上限应为 5） |
| 成交金额 | ¥616 |
| **最终库存** | **-6** |
| 库存不足拒绝 | 6（读到的是已被打负的库存——校验形同虚设） |
| 地图 API 限流误伤 | 3（外因） |

时间线：11 个请求几乎同时读到 `stock=5` → 全部放行 → `5 - 11 = -6`。
**这组数字（截图 MySQL 查询结果）就是"我先复现问题"的实证。**

### 复现路上顺手排掉的三个坑（都不是超卖本身）

1. **请求体缺字段**：`Orders.packAmount` 是 `int`，DTO 不传 → null 拆箱 → 500。
   真实前端总带全字段，压测脚本要补 `packAmount/tablewareNumber/tablewareStatus`
2. **`orders.delivery_status NOT NULL` 且无兜底**：不传 `deliveryStatus` 直接
   `ERROR 1048`。课程代码隐式依赖前端字段——真实缺陷但不在本次范围，记录不动
3. **百度地图 API 并发限流**：瞬时 40+ 次调用部分失败（店铺/地址解析失败）。
   好在失败发生在扣库存之前，不影响超卖结论；修复后串行化反而缓解了限流

## 四、③ 修复：Redis 分布式锁

### 4.1 关键设计：锁在 Controller，不在 Service

`@Transactional` 的提交发生在 Service 方法**返回之后**。锁若在 Service 内部释放，
存在「锁已释放、事务未提交」窗口——下一个请求读到的还是旧库存，超卖复发。
**锁必须包住整个事务（含提交）**，所以 `tryLock/finally unlock` 写在 Controller。

### 4.2 实现（2 文件）

**SimpleRedisLock**（`com.sky.lock`，黑马点评同款思路 + 自旋重试）：

```java
// 加锁：setIfAbsent = SET key value NX EX ttl，原子操作
public boolean tryLock(String name) {
    return Boolean.TRUE.equals(redisTemplate.opsForValue()
            .setIfAbsent(KEY_PREFIX + name, "1", LOCK_TTL)); // TTL 10s 兜底宕机
}
// 自旋版：拿不到先排队等（100次×100ms=10s），等不到才拒绝
public boolean tryLock(String name, int maxRetry, long retryIntervalMs)
```

**OrderController.submit**：

```java
if (!simpleRedisLock.tryLock("order:submit", 100, 100)) {
    throw new OrderBusinessException("当前下单人数过多，请稍后重试");
}
try {
    return Result.success(orderService.submitOrder(ordersSubmitDTO));
} finally {
    simpleRedisLock.unlock("order:submit");
}
```

### 4.3 演进过程（两版都压测过）

| 版本 | 行为 | 20 并发结果 |
|---|---|---|
| v1 快速失败 | 拿不到锁立刻拒绝 | 1 单成功、库存 4、**19 个"人数过多"** |
| v2 自旋重试 | 排队等锁最多 10s | **5 单成功、库存 0、9 个正确拒绝** ✅ |

v1 正确但吞吐代价大；v2 让请求排队串行处理，**恰好卖完库存**，拒绝的都是
真·库存不足。地图限流误伤 6 个是外部依赖问题。

## 五、已知简化（面试追问点，全部写在 SimpleRedisLock 注释里）

1. **释放锁未校验持有者**——误删他人锁风险。生产解法：value 存线程标识，
   Lua 脚本「比对再删」保证原子性；或直接 Redisson
2. **无看门狗续期**——TTL 必须大于业务最大执行时间，否则业务没做完锁先过期
3. **锁粒度是全局 `order:submit`**——串行化了所有订单。优化路径：按 dishId 分段锁
   （注意多菜品购物车按 dishId 排序获取锁，防死锁）
4. **同步自旋占用容器线程**——高并发下应换消息削峰或 Redisson
5. **另一个正解是乐观锁**：`update dish set stock=stock-#{num} where id=#{id} and stock>=#{num}`
   判断影响行数即可，单条 SQL 原子、无锁开销。本项目选 Redis 锁是练技术栈迁移，
   面试可以两案对比讲

## 七、面试怎么讲

**Q：超卖怎么防的？**
A：先加库存字段做朴素实现，压测复现超卖——库存 5、20 并发，成交 11 单、库存 -6。
然后 Controller 层 Redis 分布式锁（setIfAbsent + TTL）包住整个下单事务，自旋重试
让请求排队而非拒绝，修复后同场景 5 单成交、库存归零、零超卖。

**Q：为什么锁放 Controller 不放 Service？**
A：@Transactional 在 Service 方法返回后才提交。锁在 Service 内释放会出现
「锁已放、事务未提交」，下一个请求读到旧库存，超卖复发。我实测验证过这个边界。

**Q：分布式锁的坑？**
A：我这版有三个已知简化：释放未校验持有者（要 Lua 或 Redisson）、无看门狗续期
（TTL 须大于业务耗时）、全局粒度串行化（可按 dishId 分段，注意排序获锁防死锁）。
另外乐观锁（where stock>=n 判断影响行数）是更轻的正解，选 Redis 锁是为练技术栈。

**Q：压测怎么做的？**
A：SQL 造 20 个用户（含地址和购物车），python 按同一密钥签发 JWT，curl 并发提交。
排障中发现三个非超卖问题：DTO 缺字段致 int 拆箱 500、delivery_status NOT NULL
无兜底、百度地图 API 并发限流——都在扣库存之前失败，不影响结论。
