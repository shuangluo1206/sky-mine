## 一、先搞清楚：请求进来之后谁在做决定

所有 HTTP 请求进到后端，第一个碰到的都是 **`DispatcherServlet`**。

把它想成**公司前台**。前台手里有一张名单，写着「哪个地址由谁负责」：

```
/admin/employee/login   →  EmployeeController.login()
/admin/employee/logout  →  EmployeeController.logout()
```

- 名单上**有** → 交给对应的方法处理
- 名单上**没有** → 回一句「查无此人」，也就是 **404**

这张名单是启动时建好的，来源就是 `@RequestMapping` / `@PostMapping` 那些注解
（见笔记 02）。

**关键**：名单上只有 Controller 里的方法。所以任何**不是 Controller 方法**的东西，
默认一律 404。

---

## 二、静态资源映射：往名单里加一条特殊规则

`/doc.html` 就是那个「不是 Controller 方法」的东西。它是一个**文件**，
不是一段代码逻辑。名单上找不到 → 404。

于是需要往名单里加一条不一样的规则：

> 「有人要 `/doc.html`，别去找 Controller 了，
>  去 `META-INF/resources/` 这个位置把文件读出来直接返回。」

这就是**静态资源映射**。代码长这样：

```java
protected void addResourceHandlers(ResourceHandlerRegistry registry) {
    registry.addResourceHandler("/doc.html")
            .addResourceLocations("classpath:/META-INF/resources/");
    registry.addResourceHandler("/webjars/**")
            .addResourceLocations("classpath:/META-INF/resources/webjars/");
}
```

拆成两半理解：

| 方法 | 回答的问题 | 例子 |
|---|---|---|
| `addResourceHandler(...)` | URL 长什么样 | `/doc.html`、`/webjars/**` |
| `addResourceLocations(...)` | 去哪儿找这个文件 | `classpath:/META-INF/resources/` |

`/webjars/**` 里的 `**` 表示「后面任意多层路径都算」，
用来一次性覆盖 `doc.html` 需要的那一堆 js / css / 字体。

**一句话总结**：静态资源映射 = 告诉前台，某些地址不用找 Controller，
直接去某个位置拿文件返回。

## 三、`classpath:` 是什么意思

`classpath`（类路径）是 Java 运行时的**搜索范围**，包含两部分：

1. 自己项目编译出来的东西 —— `sky-server/target/classes/`
2. **所有依赖 jar 包的内部** —— knife4j 的、MyBatis 的、Spring 的，全算

所以 `classpath:/META-INF/resources/` 的意思不是某个具体文件夹，而是：

> 「在上面这个搜索范围里，去找名叫 `META-INF/resources` 的目录」

Java 会自己去所有 jar 里翻，翻到哪个算哪个。这就是为什么这行代码里
**没有出现任何 jar 包的名字**——写代码的人不需要知道文件具体在哪个 jar 里。

---

## 四、`META-INF/resources` 到底是什么

**它就是别人 jar 包里面的一个文件夹。** 不在我的项目里。

### 实测：把那个 jar 扒开看

jar 文件**本质就是个 zip 压缩包**，可以直接解开。

```bash
JAR=~/.m2/repository/com/github/xiaoymin/knife4j-spring-ui/3.0.2/knife4j-spring-ui-3.0.2.jar
unzip -l "$JAR"
```

输出（节选）：

```
     0  META-INF/
   134  META-INF/MANIFEST.MF
     0  META-INF/resources/            ← 就是这个目录
  1766  META-INF/resources/doc.html    ← 接口文档页面本体
  9416  META-INF/resources/img/icons/android-chrome-192x192.png
     0  META-INF/resources/webjars/js/
     0  META-INF/resources/webjars/css/
```

`doc.html` 是 **1766 字节**。而 curl 请求线上接口拿到的也正好是 1766 字节：

```bash
curl -s -o /dev/null -w "HTTP %{http_code}  %{size_download} bytes\n" \
     http://localhost:8080/doc.html
# HTTP 200  1766 bytes
```

**字节数一致 → 证明返回的就是从这个 zip 里读出来的文件。**

### 为什么偏偏叫这个名字

这是 **Servlet 规范**定的约定，不是 Spring 发明的：

> jar 包如果想往网页里塞静态文件，就放在 `META-INF/resources/` 下，
> 服务器会把它当成网站根目录来对待。

所以凡是「自带界面的第三方库」（接口文档、监控页面等）都按这个规矩放，
是行业统一约定。

## 五、坑：Spring Boot 本来是自动配好的

这一节是本篇最容易踩的地方。

Spring Boot **默认就帮你配好了静态资源映射**，会自动去这四个位置找文件：

```
classpath:/META-INF/resources/     ← 注意！第一个就是它
classpath:/resources/
classpath:/static/
classpath:/public/
```

也就是说，正常的 Spring Boot 项目**啥都不用写**，`/doc.html` 就能访问。

那为什么这个项目非写不可？看 `WebMvcConfiguration.java` 第 23 行：

```java
public class WebMvcConfiguration extends WebMvcConfigurationSupport {
```

反编译 `spring-boot-autoconfigure-2.7.3.jar` 里的 `WebMvcAutoConfiguration`，
类上有这么一个注解（实测确认）：

```java
@ConditionalOnMissingBean(WebMvcConfigurationSupport.class)
```

意思是：**容器里只要存在 `WebMvcConfigurationSupport` 类型的 bean，
我这整套自动配置就不生效。**

而 `WebMvcConfiguration` 正好继承了它、还打了 `@Configuration`
→ Spring Boot 关于 Web MVC 的全套自动配置集体退位
→ 那四个默认静态资源位置**全部失效**
→ 所以要手动把它补回来。

**结论**：那两行代码不是在配置新东西，是在**补回被自己关掉的默认行为**。

### 两种写法的区别（重要）

| 写法 | 自动配置 | 静态资源映射 | 方法修饰符 |
|---|---|---|---|
| `extends WebMvcConfigurationSupport` | **失效** | 必须手写 | `protected` |
| `implements WebMvcConfigurer` | 保留 | 白送，可不写 | `public` |

课程选前者是为了「全都自己掌控」的教学目的，代价就是要手动补这些默认行为。
真实项目里更常用后者。

### 待做实验

把第 23 行改成 `implements WebMvcConfigurer`（`addInterceptors` 和
`addResourceHandlers` 的 `protected` 改成 `public`），把两行静态资源映射注释掉，
重启看 `/doc.html` 还能不能打开。**能打开就说明自动配置回来了。**
改坏了 `git checkout` 还原。

### 顺便：这个项目里静态文件的分工

| 内容 | 谁负责 | 配在哪 |
|---|---|---|
| 后端接口 `/admin/employee/login` | Spring Controller | `@PostMapping` 注解 |
| 接口文档 `doc.html` + 它的 js/css | Spring 静态资源映射 | `WebMvcConfiguration` 这两行 |
| **管理端前端页面**（Vue 编译产物） | **nginx，完全不经过 Spring** | `nginx/nginx.conf` 的 `location /` |

前端静态文件交给 nginx 而不是 Spring，因为 nginx 读文件效率远高于 Java，
还能省掉后端的连接开销。生产环境基本都这么分。

## 六、`doc.html` 是干什么的

**它是后端所有接口的说明书网页，自动生成，还能直接在上面点着测试。**

打开 http://localhost:8080/doc.html，左边一棵接口树，点进去有「调试」页签，
参数框里填 `admin` / `123456`，点发送，右边直接出返回结果。
**以后不用再敲那些又长又难打的 curl 命令，也不用装 Postman。**

### 接口是怎么被"发现"的

文档里的接口不是手写的，是程序**扫描代码**扫出来的。
看 `WebMvcConfiguration.java` 的 `docket()` 方法：

```java
.apis(RequestHandlerSelectors.basePackage("com.sky.controller"))
```

意思是「去 `com.sky.controller` 这个包里翻」。它翻到 `EmployeeController`，
读到类上的 `@RequestMapping("/admin/employee")` 和方法上的 `@PostMapping("/login")`，
就拼出了 `POST /admin/employee/login`。参数（`EmployeeLoginDTO` 有哪些字段）、
返回值（`Result<EmployeeLoginVO>`）也一并读出来。

### 实测：把文档数据抓出来看

```bash
curl -s http://localhost:8080/v2/api-docs
```

解析后：

```
文档标题: sky外卖项目接口文档
接口数量: 2
  POST /admin/employee/login   -> login
  POST /admin/employee/logout  -> logout
```

现在只有 2 个，因为 day01 只写了登录和退出。**以后每加一个 Controller 方法，
这里自动多一条，不用手动维护。** 这也是它的第二个价值：真实项目里前端要知道
「接口地址、传什么、返回什么」，有这个页面后端就不用手写文档、不用发微信解释，
代码改了刷新页面就是最新的。

## 七、四个注解分别写在哪

上面抓出来的 `-> login` `-> logout` 是方法名，看不懂在干什么，
因为代码里没写描述注解。四个注解各管一层：

| 注解 | 贴在哪 | 作用 |
|---|---|---|
| `@Api(tags = "...")` | Controller 类上 | 给整组接口起名 |
| `@ApiOperation("...")` | Controller 方法上 | 说明这个接口干什么 |
| `@ApiModel(description = "...")` | DTO / VO **类**上 | 说明这个数据模型是什么 |
| `@ApiModelProperty("...")` | DTO / VO **属性**上 | 说明这个字段是什么 |

```java
@RestController
@RequestMapping("/admin/employee")
@Api(tags = "员工相关接口")                 // ← 加这行
public class EmployeeController {

    @PostMapping("/login")
    @ApiOperation("员工登录")               // ← 加这行
    public Result<EmployeeLoginVO> login(@RequestBody EmployeeLoginDTO dto) { ... }
}
```

## 八、`@ApiModel` / `@ApiModelProperty` 该加在哪些类上

### 项目里的实际用法统计（实测）

```
dto:     共 21 个类，其中 1 个用了 @ApiModel
vo:      共 17 个类，其中 1 个用了 @ApiModel
entity:  共 11 个类，其中 0 个用了 @ApiModel   ← 注意
```

加了的只有 `EmployeeLoginDTO` 和 `EmployeeLoginVO`——正好是 day01
登录接口用到的那两个。**entity 一个都没加。**

### 判断标准只有一条

> **这个类会不会出现在 Controller 方法的参数或返回值里？**
> 会 → 加。不会 → 加了也白加。

```java
public Result<EmployeeLoginVO> login(@RequestBody EmployeeLoginDTO employeeLoginDTO)
              ↑ 返回值里露出来了                    ↑ 参数里露出来了
```

`EmployeeLoginDTO` / `EmployeeLoginVO` 都在方法签名上，Swagger 顺着签名就能找到，
所以注解有效。

而 `Employee`（entity）只在 Service 和 Mapper 内部流转，**从不出现在 Controller
签名里**，Swagger 根本扫不到 → 给它加满注解，文档里一个字都不会多。

### 为什么 entity 不该加（更深一层）

不只是「加了没用」，是**根本不该让 entity 出现在接口上**。

`Employee` 是数据库表的镜像，里面有 `password`、`createUser`、`updateTime`
这些字段——直接返回给前端等于把表结构和敏感字段一起泄露。

这就是为什么要专门造一个 `EmployeeLoginVO`：只挑 4 个字段
（`id` / `userName` / `name` / `token`）给前端，密码留在后端。

**DTO / VO 的存在意义就是"接口的对外契约"，跟数据库解耦。
文档描述的是契约，所以注解跟着 DTO / VO 走。**

### 实践节奏

以后每写一个新接口，同步给它的 DTO / VO 加注解，照 `EmployeeLoginDTO` 的样子：

```java
@Data
@ApiModel(description = "员工分页查询时传递的数据模型")
public class EmployeePageQueryDTO implements Serializable {

    @ApiModelProperty("员工姓名")
    private String name;

    @ApiModelProperty("页码")
    private int page;
}
```

剩下那 20 个 DTO、16 个 VO **不用现在批量补**——对应的接口还没写，
补完也不知道自己补的是什么。**写到哪个补哪个。**

### 版本提醒

`@ApiModel` / `@ApiModelProperty` 属于 **Swagger 2**（包名 `io.swagger.annotations`），
本项目用的 knife4j 3.0.2 + springfox 3.0 正好是这一套。

将来升到 Spring Boot 3 + OpenAPI 3，这两个注解会换成 `@Schema`，
用法差不多但名字变了。那是「阶段二」的事，现在不用管。

## 九、为什么日志里看不见 `addResourceHandlers` 执行

对比 `addInterceptors`——它里面写了一句
`log.info("开始注册自定义拦截器...")`，启动时控制台能看到。
而 `addResourceHandlers` 一行日志都没写，所以悄无声息。

想眼见为实就自己加一句：

```java
protected void addResourceHandlers(ResourceHandlerRegistry registry) {
    log.info("开始设置静态资源映射...");
    ...
}
```

**什么时候执行**：这两个 `protected` 方法都是 `WebMvcConfigurationSupport`
留的钩子。容器启动时 Spring 构建 handler mapping 相关 bean，会回调它们——
**只在启动时执行一次，不是每次请求都跑**。

## 十、要点回顾

1. `DispatcherServlet` 拿着一张「地址 → 方法」的名单路由请求，名单上没有就 404。
2. 静态资源映射 = 往名单加一条「这个地址去某位置拿文件」的规则。
3. `classpath` = 自己的 `target/classes` + 所有依赖 jar 的内部。
4. `META-INF/resources` 是别人 jar 里的文件夹；jar 就是 zip，能解开看。
   放在这个位置是 Servlet 规范的约定，服务器会当成网站根目录。
5. Spring Boot 默认就配好了静态资源映射；本项目因为
   `extends WebMvcConfigurationSupport` 让自动配置**整套退位**，才必须手写补回来。
6. `doc.html` 是扫描 Controller 自动生成的接口文档，能在浏览器里直接调接口，
   代码改了它自动更新。
7. `@ApiModel` / `@ApiModelProperty` 只加在**会出现在 Controller 方法签名上**的
   DTO / VO；entity 不加，因为它压根不该暴露给接口。
8. 前端页面由 nginx 直接返回，不经过 Spring；只有 `doc.html` 这类
   jar 里自带的界面才走 Spring 的静态资源映射。
